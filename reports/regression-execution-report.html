SAHA-D01 · Password reset enforces a different — and in places weaker — password policy than registration

✓ Fixed & verified
Module
Authentication — Password Recovery
Catalogue cases
PWR-008 REG-016 REG-017
Component
backend/src/Saha.Application/Features/Auth/Commands/ResetPassword/ResetPasswordCommandValidator.cs
Type
Business rule / security policy

The defect (before the fix)

ResetPasswordCommandValidator requires 8–128 characters plus an uppercase letter, a lowercase letter, a digit and a special character. RegisterCoupleCommandValidator / register.schema.ts require at least 12 characters and at most 72 UTF-8 bytes, with no character-class rules. The two validators disagree in three separate directions.

What the catalogue requires

One password policy, enforced identically wherever a password is set. PWR-008 specifies 8–128 plus character classes; REG-016/REG-017 specify 12 characters minimum and a 72-byte ceiling. Whichever the product chooses, both endpoints must apply it.

Why it matters

(a) Users are locked out of their own password style. The passphrase the product markets and seeds — our quiet home by the sea — is legal at registration but rejected at reset with “must contain at least one uppercase letter”. A couple who registered with a passphrase can never reset to a similar one.
(b) Reset silently weakens the account. An 8-character password clears the reset validator, four characters below the floor registration guarantees.
(c) Silent BCrypt truncation. Registration caps at 72 UTF-8 bytes precisely because BCrypt ignores everything past byte 72 — the schema carries a comment saying so. Reset allows 128 characters, so bytes 73–128 of a long reset password are silently discarded. The user believes they set a 128-character password; the system stored 72 bytes of it.

Steps to reproduce

  1. POST /api/v1/auth/reset-password with newPassword = our quiet home by the sea → 400, “Password must contain at least one uppercase letter / digit”. The same value is accepted by POST /api/v1/auth/register.
  2. Repeat with newPassword = Abcd123! (8 characters) → the validator passes and the request reaches the code check (401 for a wrong code), proving the length rule never fired.
  3. Repeat with a 100-character password → the validator passes again; no 72-byte ceiling is applied.

Fix applied

Extracted the policy into a single PasswordRules.SharedPassword() rule now used by both RegisterCoupleCommandValidator and ResetPasswordCommandValidator, and mirrored in register.schema.ts. Per the product decision the unified rule is the character-class one: ≥ 8 characters with uppercase, lowercase, digit and special. The 72-byte BCrypt ceiling was additionally applied to reset, which previously allowed 128 characters and silently truncated past byte 72.

Evidence at the time of reporting

All three legs are API-level and deterministic — no UI timing is involved. A 401 Invalid or expired verification code response is proof the payload cleared validation, because validation runs before the code lookup.

Verified by 7 regression tests

  • auth-recovery.spec.ts:95 — a password accepted at registration is also accepted at reset passed
  • auth-recovery.spec.ts:107 — reset enforces the agreed 8-character minimum passed
  • auth-recovery.spec.ts:119 — reset requires the same character classes as registration passed
  • auth-recovery.spec.ts:131 — reset rejects passwords beyond the 72-byte BCrypt ceiling passed
  • auth-registration.spec.ts:198 — a 7-character password is rejected and 8 is accepted passed
  • auth-registration.spec.ts:214 — every character class is required at registration passed
  • auth-registration.spec.ts:232 — a password over 72 UTF-8 bytes is rejected even when under 72 characters passed
Note for the developer: Decide the single policy first, then apply it in both validators and in register.schema.ts. If passphrases are the intent, drop the character-class rules from reset and raise its minimum to 12 with a 72-byte cap. Whatever is chosen, the 72-byte BCrypt ceiling must exist on every path that hashes a password.

SAHA-D04 · Profile update lets a partner take an email address already registered to another account

✓ Fixed & verified
Module
Profile
Catalogue cases
PRF-008
Component
backend/src/Saha.Application/Features/Profile/Commands/UpdateProfile/
Type
Data integrity / uniqueness

The defect (before the fix)

PUT /api/v1/profile/me with an email that already belongs to a partner in a different couple returns 204 No Content and persists the change. Registration rejects a duplicate email, so uniqueness is enforced on create but not on update.

What the catalogue requires

PRF-008 requires email conflicts with another partner or account to be rejected atomically, consistent with the uniqueness registration already enforces.

Why it matters

Email is the recovery channel: POST /auth/forgot-password sends the reset code to both partners' addresses. Once two accounts share an address, a reset code for one couple is delivered to a person in a different couple — a cross-account account-takeover path that needs no credentials, only a profile edit. It also makes email unusable as a support identifier and can break any downstream unique index or notification routing.

Steps to reproduce

  1. Register couple A and couple B (any two complete couples with distinct emails).
  2. Authenticate as a partner in couple A.
  3. PUT /api/v1/profile/me with a valid body whose email is couple B's registrant email.
  4. Observed: 204 and the value is persisted — re-reading GET /profile/me shows the duplicated address. Expected: 409 (or 400) with no write.

Fix applied

Added ICoupleRepository.ExistsByEmailAsync(email, excludingPartnerId) and a conflict check in UpdateProfileCommandHandler, returning 409 EMAIL_IN_USE. Self-exclusion keeps re-saving an unchanged profile valid.

Verified by 1 regression test

  • profile.spec.ts:181 — a partner cannot take an email that already belongs to another account passed
Note for the developer: Needs both a uniqueness check in the update handler and a unique index on the email column, so a race between two concurrent updates cannot slip through the check.

SAHA-D15 · A failed message send silently discards what the user typed

✓ Fixed & verified
Module
Messaging
Catalogue cases
TXT-006 REL-001
Component
frontend/src/modules/messages/components/ChatThread.tsx — handleSend
Type
Data loss / error recovery

The defect (before the fix)

handleSend clears the draft immediately when the send is initiated, before the mutation resolves. When the send fails (500, timeout, offline), the message never reaches the server and the composer is already empty — the typed text is gone with no way to recover it.

What the catalogue requires

TXT-006 requires that send failures do not duplicate or lose the draft silently, and permit a safe retry. REL-001 requires that a mutation attempted offline gives accurate state and no false success.

Why it matters

This is unrecoverable user data loss on the most-used control in the product. A long message typed on a flaky connection disappears the moment Enter is pressed; there is no draft to retry, no copy in the clipboard, and no error state that preserves the text. The failure mode is worst exactly where it is most likely — mobile, in a tunnel, on hotel wifi. Users will read the empty composer as “sent” and only discover otherwise when the message never appears in the thread.

Steps to reproduce

  1. Sign in and open a partner conversation.
  2. Intercept POST /conversations/{id}/messages and force a 500 (or go offline).
  3. Type a message and press Enter.
  4. Observed: the composer is empty and the message is absent from the thread. Expected: the text is still in the composer, with an error surfaced and a retry available.

Fix applied

The draft is now cleared in the mutation's onSuccess rather than at initiation, so a failed send leaves the text in the composer to retry. Because the draft now survives an in-flight request, handleSend also guards on isPending — the Send button was already disabled during the request, but the Enter key bypassed it and would otherwise have sent twice.

Evidence at the time of reporting

The source carries a comment flagging this exact risk (handleSend clears immediately). The catalogue's TXT-006 source reference records it as a known risk to verify — this run confirms it reproduces.

Verified by 1 regression test

  • messaging.spec.ts:341 — a failed send does not silently discard the user’s draft passed
Note for the developer: Clear the draft in the mutation's onSuccess rather than at initiation, or restore it in onError. The same pattern should be checked for the edit flow, which shares the composer.

SAHA-D02 · Reset verification code accepts non-ASCII Unicode digits

✓ Fixed & verified
Module
Authentication — Password Recovery
Catalogue cases
PWR-007
Component
backend/src/Saha.Application/Features/Auth/Commands/ResetPassword/ResetPasswordCommandValidator.cs
Type
Input validation

The defect (before the fix)

The code rule is Matches(@"^\d{6}$"). In .NET, \d matches every Unicode decimal digit, not just 0-9. The Arabic-Indic string ١٢٣٤٥٦ passes validation and is forwarded to the token lookup, which answers 401 Invalid or expired verification code.

What the catalogue requires

PWR-007 requires the field to accept exactly six ASCII digits and to reject Unicode digits at validation with a 400.

Why it matters

Codes that cannot possibly match a generated token still consume a token-lookup round trip and are counted as a code attempt rather than a malformed request. That blurs the boundary between “you typed it wrong” and “this input is not a code at all”, and — where reset attempts are rate-limited or lockout-counted — lets an attacker burn a victim's attempt budget with input the validator was supposed to stop.

Steps to reproduce

  1. POST /api/v1/auth/reset-password with { "togetherIDOrUsername": "madhu", "code": "١٢٣٤٥٦", "newPassword": "ValidPass1!", "confirmPassword": "ValidPass1!" }.
  2. Observed: 401 UNAUTHORIZED — validation passed. Expected: 400 VALIDATION_ERROR.

Fix applied

Changed the code pattern from ^\d{6}$ to ^[0-9]{6}$. In .NET \d matches every Unicode decimal digit, so Arabic-Indic digits cleared validation and consumed a token lookup.

Verified by 1 regression test

  • auth-recovery.spec.ts:67 — the code must be exactly six ASCII digits passed
Note for the developer: RegexOptions.ECMAScript, or an explicit ^[0-9]{6}$ character class, restricts the match to ASCII. The same \d caveat applies anywhere else a numeric format is validated.

SAHA-D03 · Login rejects a username that carries surrounding whitespace, though the stored identity is trimmed

✓ Fixed & verified
Module
Authentication — Login
Catalogue cases
AUTH-004
Component
backend/src/Saha.Application/Features/Auth/Commands/Login/ — login handler lookup
Type
Normalisation inconsistency

The defect (before the fix)

Username.Create normalises with value.Trim().ToLowerInvariant(), so every stored username is trimmed and lowercase. Login applies only the case half of that normalisation: MADHU authenticates (200), but " madhu " is refused with 401 Invalid username or password.

What the catalogue requires

AUTH-004 requires login to apply the same normalisation as the domain value object, so leading/trailing whitespace and case variation resolve to the same identity.

Why it matters

Password managers, mobile keyboards and copy-paste routinely append a trailing space. The user sees the generic “Invalid username or password” message, which points them at their password — the one thing that is actually correct. There is nothing on screen that could lead them to the real cause, so this presents as an unexplainable login failure and drives password resets that will not help.

Steps to reproduce

  1. POST /api/v1/auth/login with { "username": "madhu", "password": "<shared password>" } → 200.
  2. POST /api/v1/auth/login with { "username": " madhu " } and the same password → 401.
  3. POST /api/v1/auth/login with { "username": "MADHU" } → 200, confirming case is already handled and only trimming is missing.

Fix applied

The login handler now normalises once — request.Username.Trim().ToLowerInvariant() — and reuses that value for both the couple lookup and the partner lookup. Fixing only the first lookup initially produced a 500, because the couple resolved while the partner did not; the regression test caught it before this shipped.

Verified by 1 regression test

  • auth-login-session.spec.ts:88 — username lookup tolerates surrounding whitespace passed
Note for the developer: Route the login lookup through Username.Create (or trim before the lookup) so one normalisation rule governs both write and read paths.

SAHA-D06 · A malformed pagination cursor silently returns the first page again

✓ Fixed & verified
Module
Messaging
Catalogue cases
THR-004
Component
backend/src/Saha.Application/Features/Messaging/Queries/GetMessages/GetMessagesQueryHandler.cs
Type
API contract / pagination

The defect (before the fix)

MessageCursor.TryDecode returns false for an undecodable cursor, and the handler simply leaves beforeTicks/beforeId null. A request for the page before an unparseable cursor is therefore answered with the newest page — the same items the client already holds — under a 200.

What the catalogue requires

THR-004 requires valid, malformed, deleted and equal-time cursors to return stable newest-first pages with no skipped or duplicated messages. A cursor the server cannot interpret is not a page boundary and must not be treated as “no boundary”.

Why it matters

An infinite-scroll client that receives a corrupted or truncated cursor — from a URL round-trip, a stale cache, or a proxy that mangles the base64 — will append messages it has already rendered and then request the same page forever. The user sees duplicated history and a scroll that never reaches the end, and because every response is 200 there is no error to surface or log.

Steps to reproduce

  1. Seed a conversation with at least three messages.
  2. GET /conversations/{id}/messages?take=2 and record the returned item ids.
  3. GET /conversations/{id}/messages?take=2&before=NOT_A_CURSOR.
  4. Observed: 200 with the identical first-page ids. Expected: 400 for an uninterpretable cursor.

Fix applied

GetMessagesQueryHandler now distinguishes “no cursor supplied” from “cursor supplied but undecodable”. The first is page one; the second is a 400, so an infinite-scroll client can no longer be handed page one forever.

Verified by 1 regression test

  • messaging.spec.ts:593 — a malformed cursor is rejected rather than silently restarting pagination passed
Note for the developer: Distinguish “no cursor supplied” from “cursor supplied but undecodable”: the first is page one, the second is a client error.

SAHA-D17 · Concurrent connection writes were unguarded by any database constraint (insert race fixed; accept/reject race still open)

✓ Fixed & verified
Module
Connect
Catalogue cases
CON-016 CON-018 REL-004
Component
backend/src/Saha.Application/Features/Connect/ — SendConnectionRequest handler + the unique pair index
Type
Concurrency — unconfirmed

The defect (before the fix)

Firing two identical POST /connect/request calls in parallel is expected to produce exactly one 201 and one 409. The assertion holds 5 out of 5 times when the test runs alone, but failed during 2 of 3 full-suite runs. The outcome is therefore load-dependent rather than deterministic.

What the catalogue requires

CON-018 requires at most one canonical relation per pair, with the losing request receiving a clean conflict rather than a second row or a 500 from the unique index.

Why it matters

Reported at low severity precisely because it is not confirmed. If the duplicate row is real, the pair-uniqueness invariant Connect depends on can be broken by a double-click or a client retry, which would then surface as duplicate cards and an ambiguous accept target. If instead the losing request is returning a 500 from the database constraint rather than a handled 409, the invariant holds but the error contract does not.

Steps to reproduce

  1. Seed two complete couples.
  2. Issue two POST /api/v1/connect/request calls for the same pair in parallel from one authenticated context.
  3. Run under concurrent load (the full regression suite) rather than in isolation — the failure does not reproduce on an idle backend.

Fix applied

Made the (CoupleAId, CoupleBId) index unique — it previously was not, so the handler's check-then-insert had no database-level guard at all — and mapped the constraint violation in ConnectionRepository.AddAsync back to the same 409 the pre-check returns. Migration UniqueCoupleConnectionPair is index-only and reversible. Pair ordering was deliberately left alone: CoupleBId identifies the recipient in the accept/reject authorization checks, so normalising it would have rewritten security logic to fix a concurrency bug. Scope: this fixes the insert race only — see the note below for the accept/reject update race that remains.

Evidence at the time of reporting

This entry is deliberately included as an unconfirmed finding rather than omitted, because an intermittent failure against a uniqueness invariant is worth a developer's eye even when the QA run cannot pin it down. Corroborating signal: the only two tests in the entire 237-test suite that needed a retry are the two Connect concurrency tests — CON-018 (racing duplicate requests) and CON-025 (racing accept vs reject). Both exercise concurrent writes to the same connection row, and no other module shows retry behaviour at all. That clustering is more consistent with a real serialisation weakness in the Connect write path than with generic test flake. The local backend is SQLite; the production target is Azure SQL, whose locking behaviour differs, so this needs re-testing against the real engine before it is dismissed.

Verified by 2 regression tests

  • connect.spec.ts:251 — two concurrent identical requests create exactly one connection passed
  • connect.spec.ts:353 — racing accept and reject settle on exactly one terminal state flaky
One linked test needed a retry. It passed, but the timing sensitivity is worth a look — see the evidence note.
Note for the developer: Partially resolved — one related race remains open. The insert path (CON-018) is now guarded by a real unique constraint and has been stable since. But CON-025 — two clients racing accept against reject on the same pending request — still needs a retry intermittently, and it is now the only Connect test that does. That is an update race on an existing row, which a uniqueness constraint cannot address; it needs optimistic concurrency (a row version / xmin check) or an explicit transaction around the read-modify-write in the accept and reject handlers. Deliberately left open rather than patched blind: the accept/reject handlers carry the authorization checks, and guessing at a concurrency fix there is how a security regression gets introduced.
